# Cookie 与 Session 详解

## 一、什么是 Cookie 和 Session？

HTTP 协议是**无状态**的：服务器默认不记得"你是谁、之前做过什么"。

为了维持"登录状态"，引入了两个机制：

| 机制 | 存放位置 | 作用 |
| ---- | -------- | ---- |
| Cookie | 客户端（浏览器） | 每次请求自动带给服务器，标记用户身份 |
| Session | 服务器端 | 记录用户的会话数据（登录状态、购物车等） |

**工作流程**：

```
1. 用户提交用户名密码登录
2. 服务器验证通过后，创建一个 Session 并生成 SessionID
3. 服务器通过响应头 Set-Cookie: sessionid=xxx 把 SessionID 下发给浏览器
4. 浏览器后续每次请求自动携带 Cookie
5. 服务器根据 Cookie 中的 SessionID 找到对应的 Session，识别出"已登录"
```

---

## 二、Cookie 的生成逻辑（爬虫必备）

爬虫中判断 Cookie 从哪来，有两个**必须记住的特征**：

### 1. 服务器生成的 Cookie

> **特征：响应头里通过 `Set-Cookie` 把值带过来。**

```python
import requests

resp = requests.get("https://example.com/login", data={"user": "alex", "pwd": "123"})

# 查看服务器下发的 cookie
for c in resp.cookies:
    print(f"{c.name} = {c.value}")
```

这种 Cookie 是**服务器主动发**的，用 `requests.Session()` 或 `resp.cookies` 就能自动获取并携带。

### 2. 浏览器（JS）生成的 Cookie

> **特征：你在响应头里找不到该值，但浏览器发请求时又有这个值。**

这类 Cookie 由页面里的 **JavaScript 动态计算生成**（比如点击、滑动、加密参数），服务器响应头里根本没有。这也是 requests 的 Session **无法维护**的 Cookie 类型。

**应对方案**：

1. **直接复制**：从浏览器 F12 → Application → Cookies 里复制出该值，硬编码到请求头；
2. **JS 逆向**：找到生成该 Cookie 的 JS 函数，用 Python 复现其逻辑（或通过 execjs/pyexecjs 调用 Node 运行 JS）；
3. **Selenium/Playwright**：用真实浏览器渲染页面，自动生成 cookie。

## 三、请求中携带 Cookie 的三种处理方式

### 方式一：直接把 Cookie 复制进请求头（简单粗暴）

```python
import requests

url = "https://example.com/member"
headers = {
    "User-Agent": "Mozilla/5.0 ...",
    "Cookie": "sessionid=abc123; name=alex",   # 从浏览器复制
}
resp = requests.get(url, headers=headers)
```

- 优点：简单粗暴；
- 问题：Cookie 有**时效性**，过期后需要重新复制。

### 方式二：用 resp.cookies 手工传递

```python
import requests

resp = requests.get("https://example.com/login", data={"user": "alex", "pwd": "123"})

# 把响应中的 cookie 传给下一个请求
resp2 = requests.get("https://example.com/member", cookies=resp.cookies)
```

### 方式三：使用 requests.Session()（推荐）

```python
import requests

session = requests.Session()

# ① 给 session 配置 headers
session.headers = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...",
}

# ② 登录，session 自动保存服务器下发的 cookie
session.post("https://example.com/login", data={"user": "alex", "pwd": "123"})

# ③ 之后的请求自动携带 cookie
book = session.get("https://example.com/member")
print(book.text)
```

**重要注意点**：

> 如果要给 session 配置 cookie，**不要在 headers 里配置**，而应在请求时传入关键字参数：`session.get(url, cookies={"name": "value"})`。因为在 headers 里配置 cookie 可能会和 session 内部管理的 cookie 冲突/被覆盖。

**session 的弊端**：

> 最大的弊端是**不能维护 JS 生成的 cookie**（原因见上文第二节）。

## 四、验证码逻辑

### 1. 验证码与 Cookie 的关系

```
1. 请求验证码图片的 URL
2. 响应头中会同时下发一个 Cookie（通常用于关联本次验证码与后续登录请求）
3. 发送登录请求时，必须带上"验证码图片响应中的那个 Cookie"
```

所以**获取验证码和提交登录，必须使用同一个会话**（session），否则验证码与登录请求对不上。

### 2. 验证码识别方案

| 方案 | 工具 | 适用 |
| ---- | ---- | ---- |
| 图形验证码 | ddddocr（开源，离线识别） | 简单数字/字母 |
| 打码平台 | 超级鹰、图鉴等 | 复杂验证码 |
| 滑块/点选 | 前端逆向 / Selenium | 行为验证码 |

```bash
pip install ddddocr
```

## 五、完整实战：验证码模拟登录

以某小说网站为例，完整演示"获取验证码 → 识别 → 带 Cookie 登录 → 访问会员页"：

```python
import requests
import ddddocr

session = requests.Session()

# 1. 配置 session 的 headers
headers = {
    "accept": "image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8",
    "accept-encoding": "gzip, deflate",
    "accept-language": "zh-CN,zh;q=0.9,en;q=0.8",
    "cache-control": "no-cache",
    "connection": "keep-alive",
    "host": "www.example.com",
    "pragma": "no-cache",
    "referer": "http://www.example.com/login.php",
    "user-agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/140.0.0.0",
}
session.headers = headers

# 2. 请求验证码图片（响应头会下发 Cookie，被 session 自动保存）
url_img = "http://www.example.com/code.php"
pre = session.get(url_img)

# 保存验证码图片
with open("captcha.jpg", "wb") as f:
    f.write(pre.content)

# 3. 用 ddddocr 识别验证码
ddd = ddddocr.DdddOcr(show_ad=False)     # 去掉广告
with open("captcha.jpg", "rb") as f:
    code = ddd.classification(f.read())  # 识别出的验证码字符串
print("验证码识别结果:", code)

# 4. 发送登录请求（自动携带验证码图片响应里的 Cookie）
url_log = "http://www.example.com/login.php"
data = {
    "username": "lzj22",
    "password": "123456789",
    "captcha": code,
    "action": "login",
    "submit": "登  录",
}
log_pre = session.post(url_log, data=data)

# 5. 登录成功后访问会员页面
member = session.get("http://www.example.com/member.php")
print(member.text)
```

> 关键点：验证码图片和登录请求共用同一个 `session`，这样验证码关联的 Cookie 才会自动带上。

## 六、Cookie 的常见属性

一个完整的 Cookie 字符串包含多个字段（分号分隔）：

```
name=alex; Expires=Wed, 21 Oct 2026 07:28:00 GMT; Path=/; Domain=.example.com; HttpOnly
```

| 字段 | 含义 |
| ---- | ---- |
| `name=value` | Cookie 的键值对 |
| `Expires / Max-Age` | 过期时间 |
| `Path` | 生效路径 |
| `Domain` | 生效域名 |
| `HttpOnly` | 只能通过 HTTP 传输，JS 读不到（更安全） |
| `Secure` | 仅在 HTTPS 下传输 |
| `SameSite` | 控制跨站请求时是否携带：`Strict`（任何跨站都不带）、`Lax`（跨站 GET 可带，默认）、`None`（全部带，需配合 Secure） |

### Cookie 的作用域（Domain / Path）

Cookie 不是"全站通用"，服务器下发时会限定它生效的范围：

| 字段 | 作用 | 例子 |
| ---- | ---- | ---- |
| `Domain` | 哪个域名下才携带 | `Domain=.example.com` 表示 example.com 及其子域名都带 |
| `Path` | 哪个路径下才携带 | `Path=/` 全站携带，`Path=/api` 只访问 /api 时才带 |

```python
# 注意：requests 不会为"其他域名"自动带某个域名专属的 cookie
resp = requests.get("https://www.example.com/login")
print(resp.cookies)   # 只含 example.com 域下的 cookie
```

> **爬虫视角**：如果"登录成功但访问接口 401"，先检查接口域名与登录域名是否一致，Cookie 有没有被限制在别的子域名下。

### 浏览器本地存储的对比（容易混淆）

| 存储 | 位置 | 大小 | 生命周期 | 是否随请求发送 |
| ---- | ---- | ---- | -------- | -------------- |
| Cookie | 浏览器 | ~4KB | 可设过期时间 | **是**（自动带上） |
| sessionStorage | 浏览器 | ~5MB | 关闭标签页即失效 | 否 |
| localStorage | 浏览器 | ~5MB | 持久保存 | 否 |
| IndexedDB | 浏览器 | 更大 | 持久 | 否 |

> 只有 Cookie 会随请求自动发送给服务器；localStorage/sessionStorage 只在**浏览器本地**用（前端保存 token、配置等），爬虫用 requests 时**不会自动带上**，需要手动读取 JS 生成的值塞进请求。

## 七、Token 认证（Cookie 之外的另一套体系）

除了 Cookie/Session，现代接口常使用 **Token（令牌）** 认证。最典型的是 **JWT（JSON Web Token）**。

### 1. Token 与 Session 的区别

| 对比项 | Session | Token / JWT |
| ------ | ------- | ----------- |
| 状态保存在 | 服务器内存/数据库 | 客户端（Token 自带状态） |
| 是否可跨服务 | 难（需共享 session 存储） | 容易（服务器只要验证签名） |
| 服务器压力 | 每个会话都占内存 | 无状态，压力小 |
| 使用方式 | Cookie 自动携带 | 放在请求头 `Authorization: Bearer <token>` |

### 2. 请求头带 Token 的写法

```python
import requests

token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.xxx.xxx"

headers = {
    "Authorization": f"Bearer {token}",   # 常见写法
    "User-Agent": "Mozilla/5.0 ...",
}
resp = requests.get("https://api.example.com/user", headers=headers)
print(resp.text)
```

> 有些接口的 Token 放在请求体、URL 或自定义头（如 `X-Token`）里，抓包时看清放在哪。JWT 由三部分组成（头.载荷.签名），中间段载荷是 **Base64** 编码，可用 Base64 解码看到内容。

### 3. JWT 解码实战（Python）

JWT 的三个部分都是 Base64URL 编码，中间"载荷"（payload）包含用户信息，用 Python 即可解出来：

```python
import base64
import json

token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoid2FuZ2hvbmd6aXVwZW5nIiwiZXhwIjoxNzAwMDAwMDAwfQ.Ui8mU9sY3x5QmX"
header, payload, signature = token.split(".")

# 补位 + 还原 +/ 再 Base64 解码
def b64url_decode(s):
    s += "=" * (4 - len(s) % 4)
    s = s.replace("-", "+").replace("_", "/")
    return base64.b64decode(s)

header_data = json.loads(b64url_decode(header))
payload_data = json.loads(b64url_decode(payload))
print("算法:", header_data["alg"])        # HS256
print("用户:", payload_data["user"])
```

> 爬虫遇到 JWT：直接解码 payload 就能看到用户信息；**签名部分无法伪造**（需要密钥），不要试图破解，老老实实从浏览器拿。

## 七·五、Cookie 的查看与调试（浏览器 F12）

爬虫最常从浏览器里"借" Cookie，方法：

1. **F12 → Application（应用）→ Cookies**：按域名查看所有 Cookie（名称、值、过期时间、HttpOnly、SameSite 等）；
2. **F12 → Network → 任意请求 → Headers**：看请求自动带上了哪些 Cookie；
3. **F12 → Console 执行**：`document.cookie` 查看当前页面 Cookie（HttpOnly 的看不到）。

```js
// 控制台直接看 cookie
console.log(document.cookie);
// 手动设置 cookie
document.cookie = "name=alex; path=/";
```

> **HttpOnly 的 Cookie**（如很多 sessionid）无法用 JS 读取，但 Network 面板能看到它被自动带上——这也是判断"该 cookie 是服务器下发的还是 JS 生成的"的依据。

### Python 侧常用操作补充

```python
import requests
from requests.utils import dict_from_cookiejar

session = requests.Session()
resp = session.get("https://example.com/login")

# 1. 查看 session 里保存的所有 cookie
for name, value in session.cookies.items():
    print(name, "=", value)

# 2. 转成字典保存到本地（下次直接复用）
cookie_dict = dict_from_cookiejar(session.cookies)
import json
with open("cookies.json", "w") as f:
    json.dump(cookie_dict, f)

# 3. 下次登录态：直接构造 session 并塞回 cookie
session2 = requests.Session()
session2.cookies.update(json.load(open("cookies.json")))
```

> 这是"Cookie 持久化"的标准套路：登录一次，把 Cookie 存文件，后续爬虫直接加载，不用每次都登录。

### Python 侧手动构造与注入 Cookie（逆向/多账号场景）

有时候没有浏览器、或 cookie 是从抓包/逆向得到的字符串，需要手动塞进 Session：

```python
import requests
from requests.cookies import RequestsCookieJar

session = requests.Session()

# 1. 把"抓包得到的 Cookie 字符串"解析后注入（分号分隔的键值对）
cookie_str = "sessionid=abc123; uid=10086; token=xyz"
for pair in cookie_str.split(";"):
    pair = pair.strip()
    if "=" in pair:
        k, v = pair.split("=", 1)
        session.cookies.set(k, v)

# 2. 指定域名注入（防止被其他域名的 cookie 干扰）
jar = RequestsCookieJar()
jar.set("sessionid", "abc123", domain=".example.com", path="/")
session.cookies.update(jar)

# 3. 直接给单个请求临时加 cookie（不污染 session）
resp = session.get("https://example.com/api", cookies={"token": "xyz"})
```

> 用 `session.cookies.set(name, value)` 注入后，之后所有请求都会自动带上——适合"浏览器里复制一串 cookie 直接喂给爬虫"的场景。注意：`cookies=` 参数只在**单次请求**生效，`session.cookies` 才是全局生效。

## 七·五·五、Cookie 反爬与风控（逆向重点）

很多网站的 Cookie 不只是"登录凭证"，还承担着**反爬校验**功能。常见套路：

### 1. 动态签名 Cookie（最典型）

服务器在响应里带一段 JS，JS 计算出某个 Cookie（如 `_signature`、`sw`、`acw_sc__v2` 等）塞给浏览器；**后续请求必须带上这个值**，否则返回 403/空数据。

```text
第一次请求  → 响应带 HTML + 一段"算 cookie 的 JS"
浏览器执行 JS → 生成 _signature=xxxx（动态变化）
再次请求    → 带上 _signature 才能拿到真实数据
```

```python
import requests

# 错误示范：第一次请求后直接发第二次，但没算 cookie
session = requests.Session()
resp1 = session.get("https://example.com")       # 返回的是"算 cookie 的 JS"
resp2 = session.get("https://example.com/api")   # 403！因为没有 _signature
```

**应对思路**：

1. **JS 逆向**：从响应里的 JS 中还原生成 Cookie 的算法（常用 `execjs` 直接执行，或手工转 Python）；
2. **浏览器渲染**：用 Playwright/Selenium 打开页面，让浏览器自动算好 Cookie，再 `context.cookies()` 取出来喂给 requests；
3. 特征识别：Cookie 名里带 `sign`/`token`/`sig`/`jsl`/`acw` 等字样的，多半是动态校验。

### 2. Cookie 混淆/加密

有的网站把 Cookie 里的值做成**加密串**，或干脆把所有值拼成一个加密字符串（如 `Cookie: v=加密内容`）。这时候：

- 先去 JS 里找这个值是怎么拼出来的（`document.cookie = ...` 处断点）；
- 或直接用浏览器渲染拿到完整 Cookie 字符串复制使用。

### 3. 风控字段（指纹、行为）

部分网站会在 Cookie 里写入**设备指纹**（`m`、`mtoken`、`gen_time` 等），由前端 JS 采集浏览器环境生成，用于判断"是不是真人/同一个人"：

```js
// 常见指纹字段：canvas 指纹、UA、屏幕分辨率、时区等拼接后加密
var fp = getFingerprint();            // 由环境信息算出
document.cookie = "m=" + encrypt(fp);
```

> 这类 Cookie 与**机器环境强相关**，从浏览器复制到 requests 通常能过；若同一环境被风控，需要保持 Cookie 与请求头（UA、IP、浏览器特征）**一致**，否则会被判定异常。

### 4. Cookie 过期与失效策略（实战经验）

| 场景 | 现象 | 对策 |
| ---- | ---- | ---- |
| 登录态过期 | 突然返回登录页/401 | 定期重新登录，或检测到 401 自动重登 |
| 动态 Cookie 过期 | 签名值失效返回 403 | 每次会话前重新计算/重新渲染 |
| 多线程共用 | 登录态错乱 | **一人一 Session**（见第七节） |
| Cookie 与 UA/IP 不一致 | 风控触发 | 保持"同一套 Cookie 配同一 UA、同 IP" |

> **判断口诀**：先分清"服务器 `Set-Cookie` 下发的"和"JS 算出来的"；前者用 Session 自动带，后者必须逆向/渲染。搞不清时，F12 Network 里对比"第一次请求的响应头"和"页面实际请求带上的 Cookie"，缺哪个就去查哪个的生成来源。

## 七·六、多线程/多进程下的 Session（高频坑）

爬虫提速常用多线程，但 Session/Cookie 不是线程安全的，常见坑：

```python
import requests
from concurrent.futures import ThreadPoolExecutor

# 错误示范：多个线程共用同一个 session，cookie 可能互相覆盖、请求串号
session = requests.Session()
session.get("https://example.com/login1")

def fetch(url):
    # 不同线程同时用同一个 session 访问不同账号接口，cookie 会乱
    return session.get(url).text
```

**正确姿势**：每个线程（或每个账号）用**独立的 Session**：

```python
def worker(url, username, pwd):
    # 每个线程自己登录、自己维护会话
    s = requests.Session()
    s.post("https://example.com/login", data={"user": username, "pwd": pwd})
    return s.get(url).text

with ThreadPoolExecutor(max_workers=3) as pool:
    results = pool.map(worker, urls, usernames, pwds)
```

> 需要"多账号分布式登录"的爬虫，一定要**一人一 Session**。跨线程共享 Cookie 轻则登录态错乱，重则触发风控封号。

## 八、小结

- Cookie 在客户端、Session 在服务端，二者通过 `SessionID` 关联；
- **服务器生成的 Cookie**：响应头 `Set-Cookie` 下发 → 用 Session 自动携带；
- **JS 生成的 Cookie**：响应头里找不到 → 需复制或 JS 逆向；
- Cookie 有作用域：`Domain` 限定域名、`Path` 限定路径；登录成功却 401 先查域名是否一致；
- 只有 Cookie 会随请求自动发送，localStorage/sessionStorage 不会；
- 验证码与登录请求必须**共用同一会话**；
- 现代接口也常用 Token（JWT）认证，放在 `Authorization` 请求头；JWT 载荷是 Base64URL，可用 Python 解码查看；
- 推荐使用 `requests.Session()` 维持登录态；配置 cookie 用关键字参数 `cookies=`，不要塞进 headers；
- **多线程爬虫一人一 Session**，跨线程共享 cookie 会登录态错乱；
- **Cookie 持久化**：`dict_from_cookiejar` 转字典存文件，下次 `session.cookies.update()` 直接复用；
- **手动注入 Cookie**：`session.cookies.set(k, v)` 全局生效、`cookies=` 仅单次请求生效，适合逆向/多账号场景；
- **Cookie 反爬**：动态签名 Cookie（`_signature`/`acw_sc__v2` 等）需 JS 逆向或浏览器渲染才能算出来；设备指纹 Cookie 要保持"Cookie+UA+IP"一致；登录态/签名过期要自动重登/重算。
